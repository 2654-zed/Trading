# D-021: Signal schema locked at sub-phase 3.1

**Date**: 2026-05-27
**Made by**: agent (per D-020 pre-staged derivative decisions, executed under sub-phase 3.1 discipline)
**Status**: ACTIVE

## Context

Sub-phase 3.1 of the multi-lens engine (per D-020 / PHASE_3_MULTI_LENS_ENGINE_SPEC.md) required defining the universal Signal contract that every lens MUST emit. The contract is load-bearing: every downstream stage (synthesis, orchestrator, feedback loop) reads Signals, and schema drift across lenses would collapse the entire pipeline.

Per **I-16**: every Signal must validate at publish time, and validation failure must be loud (not silent). This decision pins down the schema surface so the rest of Phase 3 builds against a stable contract.

## The locked schema

Implemented in `engine/core/signal_schema.py`. A `Signal` is a frozen dataclass with exactly **nine fields**:

| Field | Type | Validation |
|---|---|---|
| `id` | str | non-empty; UUID4 generated by `new_signal_id()` |
| `timestamp` | float | > 0 (Unix epoch seconds) |
| `lens` | str | ∈ `VALID_LENSES = {"stochastic", "topology", "graph", "game", "information"}` |
| `type` | str | non-empty, lens-defined taxonomy |
| `strength` | float | in [0.0, 1.0] |
| `confidence` | float | in [0.0, 1.0] |
| `time_horizon` | str | ∈ `TIME_HORIZONS = {"short", "medium", "long"}` |
| `metadata` | dict[str, Any] | dict, may be empty |
| `vector` | Optional[list[float]] | None OR non-empty list of numerics |

`validate_signal(sig)` raises `SignalValidationError` on the first violation; the bus calls it on every publish (I-16). The dataclass is `frozen=True` so signals cannot be mutated mid-pipeline.

## What this locks in

1. **Five canonical lenses**, no more, no less. Adding a sixth requires updating `VALID_LENSES` AND the orchestrator weight table + regime routing in a future decision.
2. **Strength + confidence are independent dimensions** in [0,1]. Strength = magnitude of the underlying signal. Confidence = lens's certainty the signal is real (vs noise).
3. **Three time horizons** by convention: short ≤ 5 min, medium ≤ 1 hour, long > 1 hour. Lens-defined semantics inside those ranges.
4. **`metadata` carries lens-specific detail** (addresses, computed numbers). The orchestrator MAY semantic-group on metadata keys but does NOT depend on any specific key.
5. **`vector` is optional** — when present, it's an embedding for similarity comparison in synthesis. Length is lens-defined.

## Acceptance evidence

- 18 unit tests in `engine/tests/test_signal_schema.py` pin every validation rule. Negative tests cover every invalid field shape (empty id, negative timestamp, out-of-range strength/confidence, non-dict metadata, non-numeric vector, etc.).
- Real-data validation: the sub-phase 3.1 smoke run produced 2,940 Signals against the live L3 SQLite. **Zero validation failures** (`bus.validation_failures = 0`).

## Reversal triggers

- A lens cannot express its signal cleanly within the 9 fields → propose schema extension via D-NNN naming the field. New fields require backward-compat (existing consumers must not break).
- Strength/confidence in [0,1] proves too restrictive for a future lens (e.g. a lens that produces unbounded extreme-value scores) → propose alternative normalization (e.g. z-score with documented mapping) in a D-NNN.
